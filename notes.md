### Profiling

**What's the purpose of profiling**

to see if there is things that can be predicted before we think about how to predict.

**What to profile**
- Session id
- Prompt
- Per request prefix cache hit
- Server status (running, waiting, kv cache util, throughput)
- Trajectory: [prompt][decode-0][tool_call-0][decode-1][tool_call-1][decode-2][tool_call-2][decode-3]
    - The complete trajectory timestamps of each step's start and end and queueing time. 
        - In terms of queueing time, there are two different queueing times. One is on the client side (e.g., client.py in aifsdk), and the other is vllm internal waiting queue time. I don't think the client will observe the effective queueing time unless the client is the first party who controls the concurrency of each vllm instance. If the client just dispatches the requests to the vllm instances as soon as it receives, then the client will not see the queueing time. And all the queue management and queueing time will be delegeted to each vllm instance and its internal continuous scheduler.
    - Each turn's decoded token
        - this is the important condition to the future tool calls and decoded tokens
    - Each tool call's response
        - This is going to be a part of prompt to the next decode turn.
        - Longer tool call response length means more compute, more memory bandwidth and more memory capacity in the next decode turn.
    - Each turn's decode latency
        - maybe not super important but why not. It can be also post-computed if we track the complete trajectory timeline which I want to.
        - it will be easily visible to the framework (caller) since the request after the tool call response might leave the vllm and go to the framework layer? needs to confirm. If so, then it will be treated just like a new request.
    - Each request's queueing time after the tool call response if it goes back to the infra layer router queue. needs to confirm.
    - Each tool call latency
        - Different tool call will have different latency.
        - Why it is useful?
            - It is a very important signal to the kv cache reuse distance. I will want to use it for scheduling decision. For example, the kv cache of the request following after the long tool call can be higher eviction candidate (lower priority). Again, I need to confirm how the request is treated across tool calls. Do they stay in the vllm or do they leave the vllm as a complete request from vllm perspective and go back to the client?
        - tool call time consists of ...
            - cold start time.
            - effective runtime.
            - queueing time. the tool call request might not run right away if it depends on the type of the tool call and if there is an available resources for the tool call. Otherwise, the tool call can have queueing time on the server side (not on the  vllm client side). But it is maybe not available. And not really critical. So, we don't need to worry about it.
    - Each tool call request
        - basically json that llm outputs for the corresponding tool call
    - Additional information related to the tool call
        - Even more interesting thing is that the tool call latency not only depends on the command generated by the llm (json) but also potentially depends on the data that is going to run the tool. For example, if it is going to run the tool on some input data. (e.g., grep on small file v.s. the same grep command on the large file).
        - Optional.. there could be other useful parameters in addition to the input files' size. And it is for now too much. It shouldn't be the bottleneck. I will skip it for now. There could be additional information that can help predict tool call latency.
